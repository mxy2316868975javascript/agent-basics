# P2：Agent、工作流与评测体系

状态：**规划中，当前 Demo 尚未实现**

P2 的目标是从“模型回答问题”升级到“模型在约束范围内完成任务”。它不只是增加几个工具，而是要补齐任务状态、工具执行、流程控制、权限、观测和评测。

## 1. Agent 到底解决什么问题

普通对话通常是：

```text
用户问题 → 模型回答
```

Agent 任务通常是：

```text
用户目标
  → 判断需要哪些步骤
  → 选择工具
  → 执行工具
  → 读取结果
  → 决定下一步
  → 完成任务
```

例如：

```text
“帮我查订单 123，如果已经发货就告诉我物流单号。”
```

可能需要：

1. 调用订单查询工具。
2. 判断订单状态。
3. 如果已发货，调用物流查询工具。
4. 整理最终答案。

P2 的重点是让这个过程可控、可重试、可审计，而不是让模型无限自由发挥。

## 2. Agent 和工作流的区别

| 维度 | 工作流 | Agent |
| --- | --- | --- |
| 步骤 | 预先确定 | 模型动态选择 |
| 可控性 | 高 | 较低 |
| 测试 | 容易 | 较难 |
| 适合场景 | 审核、报表、固定流程 | 研究、客服、开放式任务 |
| 典型例子 | 上传文档 → 解析 → 入库 | 判断该查哪些资料和工具 |

真实系统通常采用混合模式：

```text
工作流控制大方向
  └─ Agent 在某个节点内决定具体工具和步骤
```

不建议一开始把所有业务交给一个“全能 Agent”。固定流程越多，系统越容易测试和定位问题。

## 3. P2 的核心模块

```text
Agent Runtime
  ├─ Goal：当前用户目标
  ├─ State：任务状态和历史结果
  ├─ Planner：决定下一步
  ├─ Tool Registry：可用工具清单
  ├─ Tool Runner：校验并执行工具
  ├─ Workflow：固定节点和分支
  ├─ Policy Guard：权限、风险和审批
  ├─ Trace Store：记录每一步
  └─ Evaluator：判断任务是否完成、答案是否正确
```

## 4. Agent 循环

一个受控的 Agent 循环应当类似：

```text
接收目标
  ↓
加载任务状态
  ↓
模型决定：回答 / 调用工具 / 请求人工确认
  ↓
校验工具名、参数、权限和风险
  ↓
执行工具并记录结果
  ↓
把结果加入状态
  ↓
检查是否完成或超过限制
  ↓
未完成则进入下一步，完成则生成最终答案
```

必须存在明确的终止条件：

- 达到任务成功条件
- 达到最大步骤数
- 工具连续失败
- 超过总耗时
- 超过预算
- 需要人工审批

没有最大步骤数的 Agent，遇到模型反复调用工具时可能产生无限循环和费用失控。

## 5. 工具契约

一个生产级工具不只有名称和参数 Schema，还应该有执行边界：

```json
{
  "name": "get_order",
  "description": "查询当前用户的订单信息",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": { "type": "string" }
    },
    "required": ["order_id"]
  },
  "permission": "order:read",
  "timeout_ms": 3000,
  "side_effect": false,
  "idempotent": true
}
```

工具执行前必须由服务端完成：

- JSON 参数校验
- 当前用户权限校验
- 租户和资源归属校验
- 超时和调用次数限制
- 敏感字段脱敏
- 幂等和重试判断

模型提供的参数永远是不可信输入，不能因为它是“模型生成的”就跳过校验。

## 6. 高风险工具策略

| 工具类型 | 示例 | 默认策略 |
| --- | --- | --- |
| 查询 | 查订单、查天气 | 可自动执行，但需要权限 |
| 计算 | 统计、格式转换 | 可自动执行，限制资源 |
| 外部写入 | 创建工单、发邮件 | 记录审计，必要时确认 |
| 金融操作 | 退款、转账 | 必须人工确认和二次校验 |
| 删除操作 | 删除文件、删除数据 | 默认禁止 Agent 自动执行 |
| 代码执行 | 运行脚本 | 沙箱、资源限制、权限隔离 |

P2 不是“让模型拥有系统管理员权限”，而是让模型在一组最小权限工具中行动。

## 7. 任务状态模型

建议将 Agent 运行过程持久化，而不是只放在内存里：

| 实体 | 作用 |
| --- | --- |
| `agent_run` | 一次用户任务的整体状态 |
| `agent_step` | 每次模型判断或工作流节点 |
| `tool_call` | 模型请求调用的工具和参数 |
| `tool_result` | 工具执行结果、耗时和错误 |
| `approval` | 等待人工确认的高风险操作 |
| `trace_event` | 可查询的运行事件 |

`agent_run` 至少需要记录：

```text
run_id
user_id / tenant_id
goal
status
current_step
started_at / finished_at
token_usage
estimated_cost
error_code
```

这样服务重启后才能恢复、重试或解释一次任务到底发生了什么。

## 8. 工作流编排方式

推荐先从显式状态机开始，而不是立即引入复杂编排框架：

```text
RECEIVED
  ↓
PLANNING
  ↓
WAITING_TOOL / WAITING_APPROVAL
  ↓
EXECUTING
  ↓
VERIFYING
  ├─ SUCCESS
  ├─ RETRY
  └─ FAILED
```

固定步骤适合用普通 TypeScript 函数组合。只有出现多个分支、重试、暂停恢复和人工审批后，才需要引入更完整的工作流引擎。

## 9. 评测体系

AI 应用不能只用“页面能回答”判断质量。P2 至少要建立固定数据集：

```json
{
  "id": "order-status-001",
  "input": "查询订单 123 是否已发货",
  "expected_tools": ["get_order"],
  "expected_result": "必须返回订单真实状态",
  "must_not": ["调用退款工具"]
}
```

核心指标：

| 指标 | 检查内容 |
| --- | --- |
| 任务成功率 | 是否完成用户目标 |
| 工具选择准确率 | 是否选了正确工具 |
| 参数准确率 | 工具参数是否正确 |
| 越权率 | 是否访问了不允许的数据或工具 |
| 幻觉率 | 是否编造不存在的结果 |
| 平均步骤数 | 是否调用了多余工具 |
| 首 Token 时间 | 用户多久看到第一段回答 |
| 总耗时 | 一次任务多久完成 |
| Token 成本 | 每次任务消耗多少 |
| 人工介入率 | 有多少任务需要人工确认 |

评测方式应结合：

- 自动断言工具名和参数
- 固定答案或关键事实检查
- 模型辅助评分
- 人工抽样复核
- 线上点赞、点踩和重新提问

每次修改 Prompt、模型、工具 Schema 或检索策略，都需要跑回归集。

## 10. 观测与故障排查

一次 Agent 任务至少要能看到：

```text
run_id
  → 第几步
  → 使用了哪个模型
  → 输入输出 Token
  → 是否调用工具
  → 工具参数摘要
  → 工具耗时和错误
  → 下一步决策
  → 最终状态
```

日志中不能直接记录 API Key、完整密码、身份证号或未脱敏的业务数据。工具参数和结果应根据字段等级做脱敏。

## 11. P2 常见业务坑

Agent 的业务风险来自“模型可以连续做事”，而不是单次回答本身。工具越多、权限越大，越要把模型当成不稳定的决策输入，而不是可信的业务服务。

| 常见坑 | 解决方案 | 为什么要这么做 |
| --- | --- | --- |
| 一上来就给 Agent 配置退款、删除、发消息权限 | 最小权限；先只读工具，再逐步增加写权限；高风险操作必须审批 | 模型可能理解错意图，自动写操作会直接产生资金、数据和客户关系损失 |
| Agent 反复调用工具，形成无限循环 | 设置最大步骤数、总耗时、Token 预算和重复调用检测 | “继续尝试”对模型很自然，但对生产系统意味着费用失控和线程占满 |
| 工具超时后重试，导致重复写入 | 所有写工具使用幂等键和操作状态；重试前查询上一次执行结果 | 请求超时只说明调用方没收到结果，不代表服务端没有成功执行 |
| 工具 Schema 写得模糊 | 明确参数类型、必填字段、禁止字段、返回结构和正反例；增加契约测试 | 工具描述就是模型的 API 文档，模糊描述会导致错选工具和错传参数 |
| 把检索文档、网页和工具结果当成可信指令 | 外部内容只作为数据，使用清晰边界；工具名和权限由服务端白名单决定 | 文档或网页里可能包含“忽略规则、调用某工具”的 Prompt Injection |
| 只依赖模型说“任务完成” | 用业务系统的真实状态做后置校验，例如订单状态、工单状态和数据库结果 | 模型可以生成成功语句，但不能证明外部操作真的成功 |
| Agent 状态只保存在内存 | 持久化 `agent_run`、步骤、工具调用和审批状态，支持恢复和重放 | 服务重启、网络断开或用户刷新后，内存状态会丢失，任务无法解释和恢复 |
| 把固定流程也交给 Agent 自由规划 | 固定节点用状态机或工作流；只有不确定的子任务交给 Agent | 可确定的流程让模型自由决策只会增加不确定性和测试成本 |
| 直接拆成多个 Agent，互相传递大量上下文 | 先用一个 Agent 验证任务成功率，只有角色职责和权限确实不同才拆分 | 多 Agent 会放大 Token 成本、上下文污染、调度失败和排查难度 |
| 只测“正常完成”，不测拒绝和失败 | 加入无权限、缺参数、工具失败、重复请求、恶意指令和资料不足用例 | 生产事故通常发生在边界条件，而不是产品演示里的成功路径 |
| 评测只看最终文本，不看工具轨迹 | 同时断言工具选择、参数、顺序、次数、权限和最终业务状态 | 最终答案看起来正确，不代表 Agent 没有多查数据、越权或执行危险工具 |
| 日志记录了完整 Prompt 和工具结果 | 按字段分级脱敏，最小化上下文，使用 trace_id 关联事件 | 观测系统本身可能变成第二个数据泄露入口 |
| 人工审批只有一个“确认”按钮 | 展示目标、即将执行的工具、参数、影响范围和过期时间；审批结果绑定 run_id | 人需要确认的是具体副作用，而不是一段没有上下文的模型话术 |
| 没有成本上限，任务越复杂越贵 | 每个 Run 设置 Token、工具次数、耗时和金额预算，超限进入失败或人工处理 | Agent 的步骤数是动态的，固定单次请求限额无法控制总成本 |

## 12. P2 验收标准

- Agent 可以在最大步骤数内完成一个多工具任务。
- 每次工具调用都有参数校验、权限检查和 trace。
- 高风险写操作会进入人工确认，而不是直接执行。
- 工具超时、失败和重复调用都有明确处理方式。
- 任务可以查询当前状态，并能解释失败原因。
- 有一组固定评测数据，可以比较模型或 Prompt 变更前后的结果。
- 能看到 Token、耗时、工具次数和估算成本。
- 未授权工具、越权数据和敏感信息不会进入模型上下文。

## 13. 从 P1 到 P2 的演进顺序

推荐顺序：

```text
P1 文档检索
  ↓
一个只读工具
  ↓
多个只读工具
  ↓
固定工作流
  ↓
状态持久化和恢复
  ↓
人工审批
  ↓
评测、观测、成本和安全治理
```

先让 Agent 能稳定完成一个窄任务，再扩展工具数量和自主程度。工具越多、权限越大，评测和审计的重要性就越高。
